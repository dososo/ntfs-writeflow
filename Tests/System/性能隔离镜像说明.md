# 性能隔离真实镜像验收

入口 `性能隔离镜像.swift` **不接受任何参数**，只创建本轮新128MiB镜像、格式化该普通文件、核验hdiutil映射/虚拟属性/容量，再用生产DiskService真实读写挂载。不会读取或挂载其他介质，不强制卸载，不批量清理。

仅在新建专用目录内写4MiB。先观察真实blntfs的uid/gid/mode和FD；再验证卷外当前UID的独立APFS私有祖先、逐级NOFOLLOW、空ACL和唯一挂载实例。Python测试片段再次核对本轮镜像映射，先断言生产CLI拒绝virtual，再调用内部fio执行器顺序写/验证和完整读回。生产物理盘门禁不修改，也不提供通用旁路选项。前后身份、隔离证明和全文件摘要一致才通过；最后正常卸载、重新核验本次映射并detach。失败保留镜像与错误。

## 重现命令

在正式仓库根目录先构建固定fio并生成本机清单，路径分别为 `build/0.2.0/fio-source/fio` 和 `build/0.2.0/fio-build.json`，固定提交和清单格式见性能工具说明。扩展须已经正式签名并启用。然后：

```sh
xcrun swiftc -target arm64-apple-macos26.0 \
  -import-objc-header Tests/Performance/Benchmark-Bridging-Header.h \
  Sources/HelperShared/PrivilegedMountProtocol.swift Sources/PrivilegedHelper/HelperNamespace.swift \
  Sources/Core/VolumeRecord.swift Sources/App/Services/MountedFileSystemReader.swift \
  Tests/Performance/IsolationProbe.swift Tests/Performance/TargetProbe.swift \
  -framework IOKit -o build/0.2.0/性能目标查询
xcrun swiftc -target arm64-apple-macos26.0 -swift-version 6 -warnings-as-errors \
  -import-objc-header Tests/Performance/Benchmark-Bridging-Header.h \
  Sources/Core/*.swift Sources/HelperShared/*.swift Sources/App/Services/*.swift \
  Sources/PrivilegedHelper/HelperNamespace.swift \
  Tests/Performance/IsolationProbe.swift Tests/System/性能隔离镜像.swift \
  -o build/0.2.0/性能隔离真实镜像验收
```

为与正式客户端一致，本轮使用与已安装扩展相同团队的有效Developer ID及正式客户端标识签名；测试不修改扩展权限或助手白名单。签名名称应来自本机实际证书，不在源码固定他人的身份：

```sh
codesign --force --options runtime --timestamp --identifier com.blteam.ntfsworkbench \
  --sign "${DEVELOPER_ID_APPLICATION:?设置本机实际证书名称}" build/0.2.0/性能隔离真实镜像验收
build/0.2.0/性能隔离真实镜像验收
```

输出包含本轮镜像证据目录及完整结果JSON。镜像、fio内容、资源日志均保留。若未知提供方抢先挂载，保留拒绝原因，不切换它。

## 结果边界

2026-10-29：真实blntfs目录请求0700但观察为777，uid501/gid20；外层APFS私有父目录uid501/0700/空ACL，挂载实例唯一。4MiB内部顺序写、fio内容验证、完整顺序读回、SHA256一致和正常分离通过。不是外部物理介质、root助手namespace、Paragon同条件、正式1008GiB全套、跨驱动复读、掉电或掉线安全验收。

调试保留了两类实际失败证据：macOS ACL API返回语义与Linux不同导致额外ACL未拒绝，改为现有助手使用的空ACL规范文本比较后回归通过；Foundation对存在目录会把/private/tmp标准化为/tmp，与statfs路径不同，改为词法检查加逐级NOFOLLOW，不放宽链接限制。测试文件不参与发布应用编译。

## 管理员助手root/ACL隔离入口

`性能助手隔离镜像.swift`同样不接受参数、只操作本轮新128MiB镜像，但显式调用已经授权并运行的管理员服务。**不注册服务，不修改生产requireEnabled、服务器策略、namespace权限或UID映射。** 独立CLI缺少宿主app bundle，首次使用生产PrivilegedMountClient因SMAppService状态查询被拒绝，已保留失败并正常分离。测试适配因此直接使用相同受限NSXPCConnection、生产协议和helperRequirement；服务端仍执行原有精确clientRequirement及全部介质/挂载/身份策略。验收程序必须按正式客户端标识、同一团队Developer ID签名。

先按上文构建最新性能目标查询工具，再编译独立入口：

```sh
xcrun swiftc -target arm64-apple-macos26.0 -swift-version 6 -warnings-as-errors \
  -import-objc-header Tests/Performance/Benchmark-Bridging-Header.h \
  Sources/Core/*.swift Sources/HelperShared/*.swift Sources/App/Services/*.swift \
  Sources/PrivilegedHelper/HelperNamespace.swift Tests/Performance/IsolationProbe.swift \
  Tests/System/性能助手隔离镜像.swift -o build/0.2.0/性能助手隔离真实镜像验收
codesign --force --options runtime --timestamp --identifier com.blteam.ntfsworkbench \
  --sign "${DEVELOPER_ID_APPLICATION:?设置本机实际证书名称}" build/0.2.0/性能助手隔离真实镜像验收
build/0.2.0/性能助手隔离真实镜像验收
```

结果：2026-10-29，同团队正式签名测试入口通过既有受限XPC创建root拥有的blntfs挂载；精确的`namespace/501/UUID/volume`及根拥有的700用户层、生产只读遍历ACL、root755 UUID层、唯一挂载与祖先FD全部通过。卷内目录观察uid501/mode777，文件也映射当前用户，**没有放宽workloads文件所有权守卫**。内部执行器写4194304字节、fio校验、完整读4194304字节、全文件SHA256一致、官方CPU/RSS记录、前后隔离证明和正常卸载/detach通过。文件SHA256为`436846365cab164aff426912852e1576bb9fde5a719caad36c5f7625460e6764`。证据为`build/0.2.0/性能助手隔离真实镜像-受限XPC.log`及该日志指向的唯一镜像目录。

仍未获得真实物理盘、Paragon同条件、完整1008GiB、跨驱动或Windows复读、掉电安全结论。正式CLI依然拒绝虚拟盘；该无参数镜像入口只验证内部执行器及隔离，不提供通用virtual旁路。

## 正常只读重挂后的完整内容复核

`只读内容复核镜像.swift`不接受参数，只创建自己的128MiB镜像。先在新`WriteFlow-Benchmark-UUID`目录准备4MiB工作集及marker/原成功报告，随后调用生产DiskService正常卸载，计算整镜像SHA256，再经生产DiskService只读重挂。同驱动只读内部复核逐个读取本工具完整工作集，最后正常卸载和分离，再计算整镜像SHA256。只有RO状态、文件内容/身份、隔离证明、全镜像前后SHA和正常释放均通过才报告成功。没有自动切换第三方驱动，也不能充当实际跨驱动测试。

```sh
xcrun swiftc -target arm64-apple-macos26.0 -swift-version 6 -warnings-as-errors \
  -import-objc-header Tests/Performance/Benchmark-Bridging-Header.h \
  Sources/Core/*.swift Sources/HelperShared/*.swift Sources/App/Services/*.swift \
  Sources/PrivilegedHelper/HelperNamespace.swift Tests/Performance/IsolationProbe.swift \
  Tests/System/只读内容复核镜像.swift -o build/0.2.0/只读内容复核镜像
codesign --force --options runtime --timestamp --identifier com.blteam.ntfsworkbench \
  --sign "${DEVELOPER_ID_APPLICATION:?设置本机实际证书名称}" build/0.2.0/只读内容复核镜像
build/0.2.0/只读内容复核镜像
```

2026-10-29通过：只读完整复核4194304字节，文件SHA256为`41821a1c934edaec4c97c7a6bdd1334258bf579c829c9dd935228ee6ce534c28`；整个128MiB镜像只读周期前后SHA256均为`cb7331d0975ac487e26aacd69bbcb7dc8fb41a22944e5bdf773a13f5b7fa6312`，正常分离。证据为`build/0.2.0/只读内容复核镜像-最终.log`和摘要JSON。首次实际测试因系统Python旧版Path.stat不支持follow_symlinks在最后核验保守失败，现场已正常分离且整镜像SHA仍相同；改用兼容的os.stat后，系统Python完整回归及镜像通过，失败证据保留。

正式`benchmark.py verify`继续要求外部物理盘、实际只读挂载和内部APFS报告目的地；没有virtual旁路。镜像入口在再次核验本轮映射后只调用内部只读执行器，fixture报告不作为正式源报告。成功和拒绝路径的测试均断言没有卷内写API，宿主报告FD单独核验。真实Paragon、Windows、掉电仍待相应外部条件。
