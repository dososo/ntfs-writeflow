# 自动挂载原生机制验证

只测试本次新建64MiB普通文件镜像。Python入口不接受外部参数；每个操作核对本次镜像映射、虚拟介质与容量，失败保留镜像，不强制卸载，不清理用户文件。

原生Swift探针只对当前镜像mediaID取消一次DA默认挂载请求，再允许显式blntfs只读挂载。它独立于生产逐盘政策，不能证明自动RW、GUID可用性、竞争驱动排除或20轮实体插盘通过。正式功能不得用此探针替代验收。

## 执行

先构建固定引擎与本机启用的正式扩展，再编译：

```sh
mkdir -p build/0.2.0 build/system-tests
xcrun swiftc -target arm64-apple-macos26.0 Sources/App/Services/DiskEventMonitor.swift Tests/System/自动挂载机制.swift -o build/0.2.0/DA机制验证
xcrun swiftc -framework IOKit Tests/System/只读介质身份.swift -o build/system-tests/只读介质身份
```

探针须经同开发者正式签名以获得本应用扩展可见性；不更改扩展或助手签名白名单。然后运行 `python3 Tests/System/自动挂载机制.py`。

## 生产原生回调顺序补验

`原生事件顺序.swift/.py` 直接使用生产监控，默认无拦截规则。无参数 Python 入口仅创建本次 HFS+ 只读镜像，核对自身路径映射、实时介质编号和容量，记录挂载前探测、出现、批准与变化通知，最后摘要比较并正常分离；不合成硬件标识、不注入竞争放行、不执行读写挂载。

本机 NTFS 默认只读挂载最终失败，但补充保存真实轨迹后确认：无分区 NTFS 与 GPT 内 NTFS 均发出两次批准请求，且同代缓存命中。挂载失败不等于没有批准事件；原 HFS+ 证据不能替代 NTFS 实体自动管理。旧 HFS+ 原生样本的批准缓存原本命中；本轮红绿仅证明新增的“挂载前探测先建立缓存”要求，不声称复现旧功能必然失效。完整边界、证据与执行命令见 `发布/0.2.0自动挂载独立审查.md`。

## NTFS 默认接入轨迹补验

`NTFS默认路由.swift/.py` 只观察生产监控，不设置拦截规则。入口无设备参数；自行离线创建无分区与 GPT 内 NTFS 两种镜像，只读映射核验后再默认只读重新接入，记录同一文件系统新一代的真实批准请求。所有设备操作都绑定自身路径映射、虚拟整盘、实际容量与分区父盘；不操作其他设备。

最终结果为 `build/0.2.0/NTFS默认路由-xb27zd6c/结果.json`，受测源码、工具和脚本摘要位于同目录编译元数据。两类 NTFS 均观察到挂载前探测、出现通知和两次批准；默认挂载最终失败，所有镜像正常释放、摘要一致。文件系统描述由现有第三方驱动提供；没有真实硬件标识和生产策略，因此不是自动读写、无竞争环境或授权撤销测试通过。完整命令与仅拦截事件排队的条件性缺口见独立审查报告。

## 失败清理遗漏的纠正

早期顺序测试在挂载命令失败时尚未取得设备变量，旧清理条件因此跳过，留下 `原生事件顺序-lzzfs0es/本次.img` 的未挂载映射。此前“全部释放”概括错误；该镜像已按精确路径、虚拟属性和六十四兆字节容量核对后正常分离，未强制卸载，摘要不变。原失败与事后纠正证据保留。

现在 `原生事件顺序.py` 的 `finally` 无条件调用 `测试镜像清理.py` 按本次镜像路径回查；未知挂载或属性不符保留并报错，不根据空设备变量假定没有资源。七项模拟测试、真实 NTFS 挂载失败后的残留清理以及 HFS+ 正常清理均已复验。真实 NTFS 结果仍是“挂载失败”，清理通过单独记录。完整根因、证据路径、命令及最终精确路径回查见独立审查报告的失败清理纠正段。
