# 旧系统正常卸载补充研究

日期：2026-10-29。研究边界：只读取 Apple 官方源码、编译无系统调用的 ABI 探针；没有发送 sysctl 请求，没有挂载或卸载真实盘、镜像。本结论不改变公开支持范围。

## 结论

当前不能把 `unmount(path)`、DiskArbitration 异步卸载或 `ctlbyfsid/VFS_CTL_UMOUNT` 替换正式的 `funmount(fd)`。第三种方案可以避免按路径重新选卷，但没有把原目录 FD 与本次操作目标在内核中原子绑定；不能仅凭 root 保护目录、严格权限和助手内部串行租约证明安全等价。后续只保留研究候选，不接入生产路径。

这里区分两个命题：已经从公开实现确认“编号允许复用，事件观察 FD 不阻止原对象回收”；尚未实测证明“本产品具体 FSKit 卷上可以构造成功的误卸载”。拒绝接入依据是安全保证缺失，并非宣称已经复现攻击。

## 为什么保留 O_EVTONLY FD 仍不能作为编号租约

1. 旧版 [vfs_getnewfsid](https://github.com/apple-oss-distributions/xnu/blob/e3723e1f17661b24996789d8afc084c0c3303b26/bsd/vfs/vfs_subr.c#L1980) 使用全局 `u_short mntid_gen`，非零序列有限；只检查当前挂载列表有没有相同编号。它没有把“进程仍持有旧 FD”的编号放入保留集合。这是通用生成器的性质，不能外推为所有文件系统都必定使用同一种编号生成方法。
2. 正常卸载成功时，当前版 [dounmount](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/vfs/vfs_syscalls.c#L3113) 将挂载移出列表。旧挂载结构是否仍暂存内存，不会改变生成器只检查当前列表的事实。
3. 旧版 [vflush](https://github.com/apple-oss-distributions/xnu/blob/e3723e1f17661b24996789d8afc084c0c3303b26/bsd/vfs/vfs_subr.c#L2919) 对 `v_usecount - v_kusecount == 0` 的 vnode 允许回收；[回收逻辑注释](https://github.com/apple-oss-distributions/xnu/blob/e3723e1f17661b24996789d8afc084c0c3303b26/bsd/vfs/vfs_subr.c#L6826) 明确说明 O_EVTONLY 打开时仍可因卸载而回收。当前版有相同判断。保留这种 FD 不是阻止卸载或永久保留旧编号的内核租约。
4. 因此，旧挂载卸载以后，同类型后续挂载在编号生成序列回绕等条件下可能使用相同编号；通用代码没有以旧事件 FD 阻止这种复用。本轮没有运行大量挂载来复现这一序列。

若改持普通读目录 FD 来阻止正常卸载，就可能把自己的安全保护变成 `EBUSY` 原因；先关闭再卸载会重新产生时间窗口，强制卸载则违反本产品“正常卸载、占用拒绝”的要求。这不构成已证明的替代方案。

## sysctl 并未与原 FD 原子核对

旧版 [sysctl_vfs_ctlbyfsid](https://github.com/apple-oss-distributions/xnu/blob/e3723e1f17661b24996789d8afc084c0c3303b26/bsd/vfs/vfs_subr.c#L4860) 先按请求携带的 fsid 调用 `mount_list_lookupby_fsid`。该函数只遍历当前列表，比对两个编号字段，然后取得当前对象引用；请求不含原 FD。文件系统自身可先处理该 selector，返回 ENOTSUP 才使用通用 `safedounmount` 路径。不能假定每种文件系统处理方式完全一致。

假设时序：观察原 FD 及编号 → 原挂载被其他合法操作移除 → 同编号新挂载进入列表 → sysctl 查列表。内核会选择查询时的编号对应对象，没有再次核对原 FD。查到对象之后的引用保护解决的是该对象后续生命周期，解决不了“查到的已经是另一实例”。正式 [funmount](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/vfs/vfs_syscalls.c#L2827) 则先从调用者 FD 取得 vnode，再取得该 vnode 所属 mount，未按一个可复用编号重新选择实例。

权限也不相同：旧版 [ctlbyfsid 注册](https://github.com/apple-oss-distributions/xnu/blob/e3723e1f17661b24996789d8afc084c0c3303b26/bsd/vfs/vfs_subr.c#L5277) 未设 CTLFLAG_ANYBODY；[sysctl 框架](https://github.com/apple-oss-distributions/xnu/blob/e3723e1f17661b24996789d8afc084c0c3303b26/bsd/kern/kern_newsysctl.c#L1846) 对此类写请求要求 root，之后还可能进入 MAC 策略和卸载自身的权限检查。普通应用拿到该结构定义不代表可直接调用；本轮没有以 root 验证运行权限。

## root 命名空间、ACL 与串行租约能保证什么

这些措施能收窄普通用户替换路径、同一助手请求重叠以及意外访问的范围，适合作为多层保护。它们没有提供“所有系统挂载变更都经过本助手”的全局排他约束，不能约束物理拔盘、DiskArbitration、其他特权服务或全局编号分配。并且挂载前空目录的所有者与权限，不等于挂载后文件系统根目录和全部系统服务的权限政策。

[Apple DiskArbitration 指南](https://developer.apple.com/library/archive/documentation/DriversKernelHardware/Conceptual/DiskArbitrationProgGuide/ArbitrationBasics/ArbitrationBasics.html) 说明通知与介质行为存在顺序例外，approval 也不能保证介质持续存在。DADiskClaim、事件 FD 和观察快照有价值，但不能从这些机制推出内核 FD 与卸载目标的原子比较。

若将来采用较窄威胁模型，需要先写明允许哪些外部操作、如何保证不发生编号重用、所有系统入口如何受约束，并在对应系统和文件系统上独立审查及实测。本轮没有足够证据批准这样的契约。

- 15 项独立准备工具边界测试通过；两个固定源架构静态库及 12 个前端对象真实离线构建成功。
- 六个 ABI 对象编译通过；缺真实 macFUSE 运行时的链接按预期退出 78。

- 证据目录：`build/0.2.0/兼容后续研究/` 和 `build/0.2.0/离线可复现候选-20261029/`；生成产物未纳入源码。
- 未覆盖：实际 sysctl 调用、权限运行、正常/占用/身份变化卸载、真实 FSKit 的编号策略、旧系统和 Intel 实机、FUSE VFS 挂载及性能。
- 最小回滚：不集成任何候选；本轮生产路径零改动。撤回 `Tests/Compatibility` 新增准备工具/探针与前端入口变更即可，历史构建证据保留。
